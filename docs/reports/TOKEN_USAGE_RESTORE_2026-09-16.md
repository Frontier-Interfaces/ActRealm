### 实机复查发现的采集层缺陷

除了界面门槛，真实重启对照还定位了两处计量缺陷：

1. 同一 Codex 会话的多个恢复文件经过无序 HashMap 遍历，较旧文件的逐日数据会覆盖较新的记录。只有一个日志片段被留在日汇总里，重启会改变它。
2. 采集器没有读取新格式 `token_usage_record` 的逐响应账本；只读旧累计计数会漏掉计数器重置后的调用。

现改为：按会话合并日志片段，用原始片段时间区分重开记录、去重副本；以 thread_id 绑定所有者、以 response_id 去重响应；同一次调用的旧 token_count 镜像不再重复计入。新格式出现前的旧版数值前缀保留。没有逐响应记录的旧日志，只有明确的 compaction 边界伴随计数器下降时才进入新计数周期，普通倒退快照仍不重复计费。

已识别的大型用户文本和工具完成输出不再被误判为“缺失用量”；未知或真正超大的用量记录仍保持保守状态。响应标识和数值受采集器预算约束，超出时标为部分覆盖；不保存提示、回复、命令或完整日志。私有扫描检查点升级到 schema 6，旧缓存通过重读来源纠正。

实际日志验证：

- 一个双日志会话完整计量为 **63,442,859 Token**，与逐响应记录之和相符。
- 一个包含旧版前缀及多个恢复片段的会话为 **118,159,515 Token**，各日期/模型之和与总量一致。
- 排除当前持续写入的任务，**242 个历史会话经过三次独立进程启动，总量与逐日/模型数字完全一致**。
- 在实际安装的 Runtime 中再执行一次正常重启，**90 条历史日期/模型汇总逐项不变**，上述两条会话的总量也不变。

计量修复会产生一次历史重算；旧版导出只保留为复现对照，不作为修复后的结果。Codex 缓存仍是输入的子项、推理仍是输出的子项，均不再次加总；Claude 的缓存读取/写入按其独立口径累计。

## 删除规则

原来的归档只允许终止状态，但主列表主要保留活动/待处理任务，因此经常不可用。主任务卡现改为“删除任务”。

Native 和本机 Web 都使用 Display 的事件时间标记：保存删除时间、当前最后事件和轮次开始时间的最大值；旧快照不会让卡片重现，新事件、新轮次或更新的问题时间会恢复卡片。只改变该客户端的卡片可见性，不停止 Provider，不删除原对话或 Token 历史，也不替用户处理待批准/待回答事项。

## Claude 周额度

本机缓存同时含 `7d`（总周额度）和 `scoped_fable`（Fable 范围额度）。原来的通用时长文案将两者覆盖成同一个“1 周”。现在输出不同的范围名称和稳定标识，保留真实的两类限制。

采样缓存来自 2026-09-02。采集器现在在超过 15 分钟或已越过重置时刻后标记 stale；Native 保留这一状态，显示“上次记录”，不再改写为“可用”。增加主界面刷新入口及失败/未更新反馈。
