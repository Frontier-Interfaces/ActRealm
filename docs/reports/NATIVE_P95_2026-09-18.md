# Native p95 sampling correction — build 129

## Root cause

The old implementation sampled whenever global `eventCount` increased, but
used `max(visibleSessions.lastEventAt)` as the start timestamp. These describe
different event sets. Live diagnosis observed a new global event with an
unchanged visible-session timestamp: HTTP response time was 5.11 ms while the
timestamp was 5,580 ms old. That age could be recorded as presentation latency.
The end point was AppModel state publication, not actual screen presentation.

## Corrected measurements

Each owner WebSocket snapshot has an optional `deliveryTiming` sidecar containing
the Runtime instance, sequence, clock domain, generation start and ready times.
Both processes use the same host's `CLOCK_MONOTONIC` nanoseconds. The sidecar is
added only after deciding the factual payload changed; it does not force idle
updates. HTTP snapshots and older clients retain their existing contracts.

RuntimeClient captures receipt before decoding, then sends the immutable timing
and decoded snapshot together to AppModel. It never reads an unrelated latest
timestamp to time an earlier queued frame.

| Settings metric | Boundary |
| --- | --- |
| Snapshot arrival p95 | Runtime starts constructing this snapshot → client receives it; includes generation, serialization, transport and receive scheduling |
| UI processing p95 | Client receipt → decoding, main-queue delivery and AppModel state publication |
| Background update p95 | Actual background or resumed-window processing; excludes the time a hidden window spent waiting |

None of these values is a GPU/screen-frame completion measurement. The UI labels
and tooltips state their boundaries. Available measurements remain visible when
an older Runtime does not provide transport timing.

Each metric retains at most 100 samples over five minutes. Timer-driven expiry
also works when no new samples arrive. Initial/manual HTTP loads and the first
WebSocket snapshot after each connection are excluded from live timing. Duplicate
or reordered frames do not add samples, and changing Runtime instance resets the
previous window. Invalid optional timing never prevents task/approval decoding.
Real live durations over ten seconds are retained instead of silently discarded.

  genuine 12-second samples, legacy Runtime support and malformed timing.

- Installed native Settings first showed 262.1 ms arrival and 12.0 ms processing

  These observations validate the corrected metric boundaries, not a claimed
  rendering speedup from the old invalid 3,465 ms statistic.
- A subsequent app hide/restore check produced separate background samples.
  Final native UI observation: arrival 190.4 ms (100 samples), client processing
  11.9 ms (77 samples), background updates 6.2 ms (two samples). Hidden waiting
  did not enter the live processing window; expiring live samples reduced its
  count while arrival sampling continued.

## Settings backup compatibility found during QA

The new-provider installer stores backups in `backups/providers`, which the old
flat backup scanner rejected. This caused Settings reads to fail. The scanner
now recognizes only that specific private subdirectory and exact generated
Kimi/Grok backup names, validates all entries before any explicit clear, and
still refuses unknown files, directories and symlinks. The writer ensures both
owned backup directories are private.

A regression test covers real installer-produced backups, summary counts,
unknown-file refusal, symlink refusal and preservation of the original config.
The installed Settings page reads successfully and inventories 30 backups
(185 KB). No production backup was deleted.
